# Mandatory hard-lane execution completion

This extends accepted finality downstream execution. The six states and eleven
negative-closure requirements in RESEARCH-FINALITY.md remain authoritative.
Neither exhaustion nor lack of findings grants a no-event result.

## Scheduling and recovery

For new V5 runs the actual `research/targeting-request.json` enables mandatory
completion priority. That receipt and research packet are declared execution
checkpoint inputs. Missing actual request proof cannot acquire negative closure.
Historical runs without this receipt retain their captured scheduling behavior.

`schedule_research_actions(..., mandatory_lanes=...)` retains exact-provider
preferences and complementary roles, then alternates required native strategies
between mandatory lanes before optional/general waves. One general opportunity
is protected when executable general work exists. An actual general opportunity
in epoch 0 satisfies that edition-wide reservation; epoch 1 can use its full
remaining cap for mandatory work. Existing priority/fairness orders remaining
capacity. Scheduler telemetry identifies this policy and required allocations.

The existing limits remain eight actions per epoch, at most two epochs,
sixteen per edition. Per-job search, fetch, follow-up and round limits remain
in effect. Insufficient combined capacity is a real blocker, never a hidden
extra allowance. Other breadth and evidence requirements still block handoff.

Epoch 1 also admits unchanged, partially executed hard needs. Continuations
carry their original action IDs, request lineage, job ID, search/fetch/follow-up
counters, round number and completed native strategy indices. Completed actions
are excluded. A completed hard lane is not reopened. A job whose round limit
is exhausted cannot gain another round. Successful upstream artifacts remain
checkpoints; no epoch 2 is created.

Fresh acceptance replay derives mandatory lanes from the archived actual request
and reconstructs prior general opportunities from executed actions. Production
and replay share `merge_required_research_continuations` so carried counters,
unchanged needs and changed-need lineage materialize identically after the source
run directory is removed. Revision and implementation-hash checks remain intact.

For mandatory protocols the executor completes scheduled core work before
recursive follow-ups. An already-observed dynamic extraction failure receives
first follow-up priority; ranked exact discovery-lead inspection precedes
optional navigation/channel expansion. All dispatches consume the same shared
RoundActionBudget and existing job allowance.

## Dynamic extraction

A static SOURCE_DYNAMIC_ROUTE_REQUIRED observation materializes one explicit
FETCH_URL recovery action with `extraction_route=DYNAMIC` and parent observation
lineage. It uses the existing exceptional `ExtractionFallback` callable via the
safe `fetch_and_extract_source` boundary. It cannot recursively retry itself.
Recovered text returns through ordinary source, semantic, temporal, role,
independence and candidate validation. Extraction grants no evidence shortcut.

The production optional adapter remains **disabled / NOT_RUN**. No browser
backend, paid provider, dependency or service is installed/enabled by this
change. `discovery_adapter_from_config` accepts an explicit extractor only when
the existing fallback configuration is enabled and integration-test PASS.
Without a supplied proven callable, dynamic acquisition reports
SOURCE_DYNAMIC_ADAPTER_UNAVAILABLE. Failed/inadequate extraction remains an
explicit technical failure. Fixtures demonstrate both recovery outcomes; they
do not certify an unattended browser integration.

Previously untimestamped mandatory adapter results now record the observed
attempt start when the adapter supplied no observation timestamp. Chronological
failure resolution still requires a later successful acquisition of the same
exact request. The original failure and resolving observation remain auditable.

## Discovery-lead disposition

Each potential lead receives an explicit inspection/capacity/technical/contract
resolution. Scope or semantic rejection requires actual exact-page content and
hashes, using the existing classifiers. Date rejection requires captured
temporal evaluation. Deduplication requires the identical exact URL and inspected
content proof. Different URLs on the same origin remain separate potential
events. Unsafe targets are contract blocks, not absence.

An inspected qualifying lead proceeds to ordinary evidence evaluation. An
uninspected potential lead gets a required exact-fetch request plus an explicit
capacity reason. Selected-but-unexecuted requests remain blocked. Every such
request and failed dynamic recovery stays in the durable action ledger.

Finality reconciles cross-epoch exact inspections in a derived observation view,
without editing earlier checkpoints. Search observations remain discovery
leads; rejection never upgrades their source/evidence role. This fixes stale
pending-parent bookkeeping while retaining all proof requirements.
